# Assignment 1 学习笔记：广义五子棋与对抗搜索

> 对应课程第 4 章「对抗搜索与博弈」。本笔记依据作业 PDF 整理，用于理解、设计、测试和撰写报告；实际代码应独立完成。

## 1. 作业要完成什么

本作业不是实现固定的「15×15、五连」游戏，而是实现**广义五子棋**（`(N, K)`-Game）：

- 棋盘是 `N × N`，作业常用范围为 `5 ≤ N ≤ 15`；默认示例是 `N = 15`。
- 黑棋 `1` 先行，白棋 `2` 后行；`0` 表示空位。
- 任意横、竖、主对角线、次对角线上形成 **K 个及以上**同色连续棋子即胜。长连也算胜，没有禁手。
- 棋盘满且无人获胜为和棋。
- `N` 和 `K` 由构造函数/命令行传入，不能在算法中写死 `15`、`5` 或“五连”。

需要交付两件事：

1. 一个可玩的游戏程序，支持：人人对战、人机对战、机机对战；CLI 或 GUI 均可。
2. 一个能被课程裁判加载的 AI 文件 `assignment1/gomoku_ai.py`，其中必须有 `GomokuAI` 类和规定的接口。

提交目录最低应包含：

```text
assignment1/
├── gomoku_ai.py       # 必需：裁判直接加载
├── main.py            # 必需：游戏入口；也可拆分 main_cli.py 等
├── gomoku_game.py     # 推荐：规则与棋局状态
├── random_ai.py       # 已提供，可用于测试
├── requirements.txt
└── report.md
```

`arena.py` 是课程提供的本地裁判，不是最终要实现的 AI；建议保留它用于验收。作业 PDF 写明的截止时间是 **2026-10-11**，以截止前 GitHub 仓库 `assignment1/` 的最后一次 push 为准。

## 2. 统一协议：先保证“能被裁判正确调用”

裁判会直接导入 `assignment1/gomoku_ai.py`，所以文件名、类名和方法签名不能修改。

```python
class GomokuAI:
    def __init__(self, player_id: int, board_size: int, win_length: int):
        ...

    def get_move(self, board, last_opponent_move, time_limit):
        ...  # 必须返回 (row, col)
```

### 2.1 参数含义

| 项目 | 含义 | 实现注意点 |
|---|---|---|
| `player_id` | 本局本 AI 的棋色；`1` 为黑、`2` 为白 | 对手恒为 `3 - player_id` |
| `board_size` | 棋盘边长 `N` | 循环边界、中心点、数组大小均依赖它 |
| `win_length` | 获胜长度 `K` | 胜负检查、评估函数窗口都依赖它 |
| `board` | `N × N` 二维 list，元素为 `0/1/2` | 把它当作只读；搜索时在自己的副本上落子/撤子 |
| `last_opponent_move` | 对手刚下的 `(row, col)`；先手第一步为 `None` | 可用于优先生成邻近候选点，不应成为唯一依据 |
| `time_limit` | 本手墙钟时间上限（默认赛制 5 秒） | 搜索必须主动提前停止，不能等裁判中断 |

`get_move` 的返回值必须是 `(int, int)` **元组**，坐标从左上角 `(0, 0)` 开始。不要返回字符串、`None`、浮点数，也不要返回已经有棋子的坐标。

### 2.2 裁判怎样判负

以下任一项都会立即判负，算法下得再强也无效：

1. **超时**：`get_move` 在时限内未返回。
2. **非法落子**：不是坐标二元组、坐标不是整数、越界、或目标格已被占用。
3. **运行异常**：构造函数或 `get_move` 抛出未捕获异常。

因此每次决策前都应保留一个永远合法的后备着法，例如扫描得到的第一个空位；如果深度搜索因时间不足被中断，就返回最近一次“完整搜索层”得到的后备结果。

### 2.3 `arena.py` 的作用

它负责创建棋盘、轮流调用两个 AI、计时、验证落子、检查胜负并输出结果。典型命令：

```bash
# 自己的 AI 对随机 AI
python arena.py gomoku_ai.py random_ai.py --board 15 --win 5

# 小棋盘快速测试；--quiet 只输出结果
python arena.py gomoku_ai.py random_ai.py --board 9 --win 4 --time 1 --games 2 --quiet
```

参数 `--board`、`--win`、`--time`、`--games` 是很重要的回归测试维度。应至少测不同的 `(N, K)`，而不是只测默认配置。

## 3. 游戏规则模块：状态、合法着和终局

把 UI、AI 和规则分开会显著降低 bug 的数量。`gomoku_game.py` 可以只负责规则，不负责打印或搜索。

### 3.1 一个博弈状态应包含什么

一个状态 `s` 至少包括：

- `board`：当前棋盘；
- `current_player`：当前轮到谁；
- `last_move`：上一手坐标（可选，但胜负检查会更快）；
- `moves_played` 或空位数：用于判和棋。

合法着集合为：

$$
A(s) = \{(r,c) \mid 0 \le r,c < N,\; board[r][c] = 0\}
$$

落子是不可逆的；在搜索内部可使用“原地落子 + 撤销落子”，但游戏真实状态只能在确认一手后更新。

### 3.2 K 连检查：四个方向即可

不需要从每个格子重复检查。只要检查**刚刚落下的棋子**，分别统计下列方向的正反两侧：

```text
(0, 1)   水平
(1, 0)   垂直
(1, 1)   主对角线
(1,-1)   次对角线
```

对某一方向 `(dr, dc)`：从落点向正方向数连续同色棋子，再向反方向数连续同色棋子，加上落点自身。若总数 `>= K`，则获胜。必须是 `>= K`，因为题目规定长连也胜。

该方法每一方向至多走到棋盘边界，单次检查复杂度为 `O(N)`；比每回合扫描全棋盘更合适。

### 3.3 三种游戏模式

| 模式 | 黑方来源 | 白方来源 | 要点 |
|---|---|---|---|
| 人人 | 人类输入/点击 | 人类输入/点击 | 输入后调用统一的合法性与胜负检查 |
| 人机 | 人类或 AI | AI 或人类 | AI 使用 `GomokuAI.get_move`；人类可选执黑或白 |
| 机机 | 一个协议 AI 文件 | 另一个协议 AI 文件 | 自动循环到胜/和；适合做实验 |

无论模式如何，最终都应复用同一套 `play_move`、`check_win` 和 `is_draw` 规则，避免 GUI/CLI 与裁判规则不一致。

## 4. 五子棋为何适合对抗搜索

这是一个双人、零和、完全信息、轮流行动、确定性的博弈：双方都能看见完整棋盘；没有骰子或隐藏牌；一方取得优势对应另一方的劣势。

可将它形式化为：

- 状态集合 `S`：所有合法棋盘和轮次；
- 初始状态 `s₀`：空棋盘，黑棋行；
- 行动集合 `A(s)`：空格坐标；
- 转移函数 `Result(s, a)`：在空格 `a` 落当前方棋子；
- 终局测试 `Terminal(s)`：一方 K 连或棋盘满；
- 效用 `U(s)`：从“本 AI”视角，胜为正、负为负、和为零。

完整博弈树极大。例如空 15×15 棋盘的第一层就有 225 个分支，第二层约 224 个；不可能搜索到终局。因此必须使用候选着、深度截断和启发式评估。

## 5. MiniMax：在假设对手也理性时选棋

MiniMax 的核心不是“找到我下一手最高分”，而是“找到即使对方随后尽力反制，我仍最有保障的一手”。

设 `V(s)` 是从本 AI 视角的状态价值：

$$
V(s) =
\begin{cases}
U(s), & s \text{ 为终局} \\
\max_{a \in A(s)} V(Result(s,a)), & \text{轮到本 AI} \\
\min_{a \in A(s)} V(Result(s,a)), & \text{轮到对手}
\end{cases}
$$

- **MAX 层**：本 AI 选分数最大的子节点；
- **MIN 层**：对手选使本 AI 分数最小的子节点；
- 根节点最终返回分数最高的着法，而不是只返回分数。

### 深度截断

若只搜索到深度 `d`，还未终局的叶节点不能再调用真实胜负效用，必须调用评估函数 `Eval(s)`。这就是“深度受限 MiniMax”。

```text
search(state, depth, player):
    若 state 是终局：返回真实胜负分数
    若 depth == 0：返回 Eval(state)
    若 player 是我方：返回所有子节点分数的最大值
    否则：返回所有子节点分数的最小值
```

深度越大，能看见的战术越多，但节点数通常接近 `b^d`（`b` 是候选分支数）。所以“加深一层”可能使耗时成倍增加。

## 6. Alpha-Beta 剪枝：MiniMax 的必要加速

Alpha-Beta 与完整 MiniMax 得到**相同的选择**，只是不再展开已经不可能影响最终决定的分支。

- `alpha`：MAX 目前已知的最好下界；MAX 至少能拿到这个分数。
- `beta`：MIN 目前已知的最好上界；MIN 至多允许这个分数。
- 当 `alpha >= beta` 时，继续查看当前节点剩余兄弟节点没有意义，立即剪枝。

```text
alphabeta(state, depth, alpha, beta, player):
    若终局或 depth == 0：返回对应分数

    若 player 是 MAX：
        value = -∞
        对每个候选着：
            value = max(value, alphabeta(child, depth-1, alpha, beta, MIN))
            alpha = max(alpha, value)
            若 alpha >= beta：停止循环
        返回 value

    若 player 是 MIN：
        value = +∞
        对每个候选着：
            value = min(value, alphabeta(child, depth-1, alpha, beta, MAX))
            beta = min(beta, value)
            若 alpha >= beta：停止循环
        返回 value
```

**易错点**：递归时必须先落子，递归结束后无论正常返回还是提前剪枝，都要撤回该子；`alpha`/`beta` 更新的是当前层的界，不是全局固定分数。终局分值应远大于普通启发式分值，这样“必胜”不会被普通棋型分数覆盖。

## 7. 候选着生成与着法排序

### 7.1 为什么不搜索所有空格

五子棋的有效落子通常在已有棋子附近。远离所有棋子的格子短期内既不构成连子，也不阻止对手。若每层都枚举所有空格，Alpha-Beta 也会太慢。

常用候选着生成策略：

1. 空棋盘时，优先中心点 `(N // 2, N // 2)`；这是一般性启发，不是针对固定棋盘的应答表。
2. 非空棋盘时，收集每个已有棋子周围半径 `R`（常从 1 或 2 开始）的空格并去重。
3. 若候选数仍然太大，按启发式排序后只保留前 `B` 个；`B` 是可调参数。
4. 保证兜底：候选集合意外为空而棋盘仍有空格时，退回所有空格或首个空格。

半径、候选上限与 `N` 有关，不能让算法只在一个棋盘尺寸上工作。候选过滤会牺牲少量全局着法，但换来更深、更有价值的搜索。

### 7.2 着法排序为何重要

Alpha-Beta 越早先搜到好着，越早提高 `alpha` 或降低 `beta`，剪枝越多。常见优先级是：

1. 我方一步直接获胜；
2. 对手下一步会直接获胜的堵点；
3. 我方能形成 `K-1` 连、活三等强威胁的位置；
4. 阻止对方强威胁的位置；
5. 邻近已有棋子、靠近棋盘中心的位置。

排序只影响速度，不应改变 MiniMax 的理论结果。对于被截断的搜索，排序也会让有限时间优先看见更关键的变化。

## 8. 评估函数：未下完时如何给棋局打分

搜索到深度边界时，评估函数用于近似“这个局面对我有多好”。评估应当始终从本 AI 的视角返回一个数：正数偏向我方，负数偏向对手，零表示大致均衡。

### 8.1 基本思路：扫描长度为 K 的窗口

对每一个起点、每一个方向，只检查不会越界的长度为 `K` 的连续窗口。统计窗口中：

- `my_count`：我方棋子数；
- `opp_count`：对手棋子数；
- `empty_count`：空格数。

规则示例：

- 同一窗口同时有双方棋子，称为**被阻断窗口**，通常不给潜力分；
- 只含我方棋子和空格，按 `my_count` 加分；
- 只含对手棋子和空格，按 `opp_count` 扣分；
- `K-1` 加一个空格是几乎成棋的威胁，权重应明显高于一般连子。

抽象形式：

$$
Eval(s)=\sum_{w \in windows} f(my(w)) - \lambda f(opp(w))
$$

其中 `f(t)` 可随连子数快速增长（如指数或手工表），`λ` 可略大于 1，让防守对手的致胜威胁更积极。重点不是某一组固定数字，而是保证“更多连续同色子、更多可延伸空间、距离 K 更近”获得更高权重。

### 8.2 活棋、眠棋与双威胁

只数连续子数还不够，因为两端是否可延伸很关键。

- **活 L**：一段连续 L 子的两端都为空，未来可向两端延伸；
- **眠 L**：只有一端为空，发展空间较小；
- **冲 K-1**：一端被堵但只差一手成 K，依然必须高度重视；
- **双威胁**：一手可制造两个独立的强威胁，对手一手通常防不住。

在实现上，可围绕每颗棋子沿四方向取得一条局部线，计算连续数及两端格；或在 K 窗口评分基础上额外识别开放端。无论方案如何，所有“接近胜利”的判断都必须使用变量 `K`，不能把“活四”写成唯一特殊规则。

### 8.3 终局分与评估分要区分

终局不是普通 `Eval`：

- 我方已胜：极大的正数；
- 对方已胜：极大的负数；
- 和棋：0 或接近 0。

可在胜负分中加入/减去剩余深度，使“更快获胜”和“更晚失败”略优，但最重要的是终局绝对优先于棋型分数。

## 9. 时间管理与迭代加深

裁判按墙钟时间计时，不能把全部 `time_limit` 用尽。Python 的调度、系统负载和一次递归返回都可能带来额外延迟。

### 9.1 安全的时间预算

在 `get_move` 开始时：

1. 记录 `start = perf_counter()`；
2. 设置 `deadline = start + time_limit - safety_margin`；
3. 在递归入口和候选循环中反复检查当前时间；
4. 到达截止点时，抛出内部超时信号或立即结束本轮搜索；
5. 捕获内部超时，只返回此前已经完成的结果，不让异常逃出 `get_move`。

`safety_margin` 需随时间限制合理设置。5 秒时可以留出明显余量；1 秒或更短时更应保守。外部裁判看到的不能是“内部 Timeout 异常”，而必须仍是一个合法坐标。

### 9.2 迭代加深（加分方向）

迭代加深是按深度 1、2、3……重复运行完整的 Alpha-Beta：

```text
best_move = 一个已验证合法的候选着
for depth = 1, 2, 3, ...:
    在截止时间前完成 depth 层搜索
    若本层完整完成：best_move = 本层根节点最佳着
    否则：停止
return best_move
```

它解决了固定深度的难题：有时间就自动加深；没时间时总有上一个完整深度的答案。上一轮最佳着还可放到下一轮排序首位，从而帮助 Alpha-Beta 更快剪枝。

## 10. MCTS 与 UCT（可选加分）

蒙特卡罗树搜索（Monte Carlo Tree Search, MCTS）并不要求实现，但作业允许作为进阶方向。它更适合动作空间大、评估函数难设计的场景。

每轮 MCTS 通常有四步：

1. **Selection 选择**：从根向下，用 UCT 挑选兼顾利用与探索的子节点；
2. **Expansion 扩展**：为未完全展开的节点加入一个新合法着；
3. **Simulation/Rollout 模拟**：从新节点快速模拟到终局或截断；
4. **Backpropagation 回传**：把本次胜负/回报更新到路径所有节点。

常见 UCT 公式：

$$
UCT_i = \frac{W_i}{N_i} + c\sqrt{\frac{\ln N_{parent}}{N_i}}
$$

- `W_i / N_i`：子节点历史平均收益（利用）；
- 第二项：访问少的节点获得探索奖励；
- `c`：探索强度超参数。

在五子棋中，纯随机 rollout 往往棋力较弱；可以用“立即赢/立即挡”的轻量策略改善，但仍要处理时间预算和合法候选集合。对于本作业，先写稳定的 Alpha-Beta 基础版通常比仓促加入 MCTS 更可靠。

## 11. 推荐的开发与验证顺序

1. 写并测试通用规则：合法落子、四方向 `>= K` 胜负、满盘和棋。
2. 完成 CLI 的人人对战，确认不同 `N/K` 配置都正确。
3. 在 `gomoku_ai.py` 中先实现“永远返回合法空位”的最小版本，确保协议没有问题。
4. 加入“一步赢”和“一步堵”的战术检测，先稳定胜过 `random_ai.py`。
5. 加入候选着、深度受限 MiniMax、Alpha-Beta 与评估函数。
6. 加入计时检查与迭代加深；在短时限下也不能崩溃或非法。
7. 接入人机、机机模式并收集实验数据。

### 建议测试矩阵

| 测试 | 目的 |
|---|---|
| `5×5, K=3` | 盘面小、终局快，适合发现胜负检查/递归错误 |
| `9×9, K=4` | 适合快速进行多局 AI 回归测试 |
| `15×15, K=5` | 默认配置，观察真实性能 |
| `15×15, K=6/7` | 检查是否真的没有把 K 写死为 5 |
| `--time 1` | 检查时间管理与兜底返回 |
| AI vs random，20 局以上 | 报告要求的基础胜率/平均耗时数据 |
| 自我对战 | 检查先后手偏置、平均对局长度与是否会卡死 |

## 12. 报告应写什么

`report.md` 需要的不只是截图或胜率。建议按照 PDF 的四部分组织：

1. **总体设计**：模块图/职责；三种模式的流程；`N/K` 从哪里进入游戏与 AI。
